HOYA Market Agent

有界推理的加密市場分析 Agent
Python 3.12 Pydantic v2 Amazon Bedrock Streamlit EC2

開場（30 秒）：現場才公布題目與幣種，15 分鐘，原則上只有一次執行機會。我們做的不是一個更會講話的 Agent，是一個把自己每一步都攤開來讓人查的 Agent。

支援 BTC / ETH / SOL / BNB / XRP，一次一至兩幣。900 秒硬上限，四項固定 artifacts。

操作提示：N 開關講稿、A 跳到附錄、方向鍵或 Space 換頁、Ctrl+P 匯出 PDF。

題目的真正難點

難的不是「答得出來」
是「答了憑什麼信」

  • 01數字是編的　模型算的還是想的，查不出來
  • 02矛盾被抹平　敘事順暢的代價是吃掉反方證據
  • 03失敗變成幻覺　API 掛掉時安靜補一段合理的假話
所以目標從「產出一份分析」換成 產出一份能被逐條驗證的分析。

核心轉折（60 秒）：任何 LLM 都能生出一份看起來很專業的市場分析。問題是評審沒辦法驗證它——這才是這個題目真正的難點。

三種失敗模式都不是「模型不夠聰明」，而是「系統沒有結構去擋」。所以我們的答案不在 prompt，在架構。

要能被驗證的四件事：資料從哪來、怎麼推論、哪些證據互相衝突、哪些限制會影響結論。後面每一頁都在回答其中一項。

價值主張（45 秒）：產品定位不是預測價格，而是「在時限內交出一份知道自己哪裡不知道的分析」。

四個數字逐一講：100% 是可回溯率——每個結論都指得到 Evidence ID，指不到就明確標 insufficient_data=true，不含糊帶過。

0 是最關鍵的一個：所有報酬、波動、回撤、量能 z-score 全部由 deterministic Python 算，LLM 連補值都不行。缺 bar 就標 unavailable，不 forward-fill 硬湊。

3 次 LLM 呼叫是上限不是平均——Planner、Research 抽取、Arbiter 各一次，沒有 agent loop。

核心設計

有裁量權，但沒有權限

LLM 會做

  • 從靜態允許清單挑操作
  • 引用工具算出的數值
  • 引用 Evidence ID 組主張
  • 固定六階段各跑一次

Deterministic 擋掉

  • 自造 provider 或 API 網址
  • 自由 agent loop
  • 補值、猜值、自造數字
  • 把自己輸出當證據
  • 延長 deadline

這是全場最重要的一頁（60 秒）：一般 Agent 的賣點是「它能自己決定做什麼」。這裡的賣點相反——它能自己決定做什麼，但能做的事情是一個事先固定、有限的集合。

關鍵在最後一句：劃定這個範圍的那段程式，不接受 LLM 或外部內容修改。 allowlist 是靜態設定檔，沒有 runtime plugin discovery、沒有遠端 registry、沒有動態註冊。

如果評審只記得一句話，希望是這句：LLM 在這個系統裡有裁量權，但沒有權限。

架構主線（60 秒）：六個固定階段、單次通過、沒有回圈。Market Worker 完全不碰 LLM，是純 Python 工具鏈；Research Agent 只做一次語意抽取。

並行的意義：asyncio fork-join，兩條分支各自有獨立 timeout。新聞源掛掉不會拖垮市場證據，反之亦然——這是 partial result 的基礎。

證據先落盤很重要：evidence.json 在 Ledger 完成當下就寫，不等 Arbiter。所以就算推理階段整個失敗，可追溯性還在。

Pydantic v2 全面 extra="forbid"——這不是預設值，是刻意選的。

LLM 出現的位置

三次呼叫，全部結構化輸出

① PLANNER

決定查什麼

只收題目與可用能力，產出 ResearchPlan。

禁止 下市場判斷、指定清單外的工具或網域。

② RESEARCH

資料變事實

只收有界的 source records，產出引用 record ID 的 EvidenceDraft[]。

禁止 瀏覽網頁、自創 URL、捏造內容。

③ ARBITER

證據變結論

只收排序後最多 30 筆 Evidence，產出 AnalysisResult。

禁止 自造數值、繞過 Evidence ID、改寫可信度。

輸出先過 Pydantic 驗證才准進入系統核心。修 1 次仍不過，走 deterministic fallback。

邊界的具體化（50 秒）：三次呼叫都走 Bedrock Converse 的 structured output，都有明文的「不能做」清單寫在 prompt 與程式兩邊。

驗證關卡：schema 正確、所有 evidence/claim 引用可解析、claim graph 無環（DAG）、confidence 沒超過 deterministic 上限——四項全過才算數。

未通過驗證的原始 LLM 輸出，永遠不會進入 Renderer 或 artifacts。schema repair 花的是同一個 stage 的剩餘預算，不是額外預算——這點在附錄 A2 有完整時間表。

Arbiter 只餵 normalized fact 與 Evidence ID，不餵無界原始網頁——這同時是成本控制與 prompt injection 防線。

憑什麼可信

四道硬邊界

邊界 ①

輸入信任

題目與外部回傳一律當資料，不當指令。「忽略上述規則」只會被當字面內容。

邊界 ②

工具

ToolRegistry 是靜態映射。無動態註冊，LLM 不能新增 provider 或網域。

邊界 ③

證據

LLM 產物永遠不是證據。可信度由靜態表指派，producer 自己都不能宣告。

邊界 ④

時間

預算由單調時鐘推導。Planner 完全不碰時間，跳過順序寫死。

把預算交給 LLM 分配，正是這個設計刻意避免的事。

信任邊界（60 秒）：這四道就是「憑什麼可信」的實體。

① 輸入信任：外部 payload 在通過 schema 驗證前只是 bytes；驗不過就記成 typed degradation，永遠不會變成事實進入 Claim 或報告。這是 prompt injection 的結構性防線，不靠「請不要聽從指令」這種句子。

③ 證據邊界的細節：EvidenceDraft 上根本沒有 reliability 欄位——不是不填，是欄位不存在。producer 只提供 source_class 與發布者資訊，Evidence Processor 是唯一指派可信度的地方。這種「讓錯誤無法表達」的設計比執行期檢查強。

④ 時間邊界：常見誤解是「Planner 分配 900 秒」。不是——所有 stage deadline 由 DeadlineManager deterministic 推導，Planner 只輸出回看窗、證據類型與步驟清單。

證據模型（60 秒）：最反直覺、也最重要的設計：EvidenceItem 本身沒有立場。supports / opposes / neutral 只存在於 Claim-Evidence Link。

為什麼這樣設計：「這則新聞是利多」不是新聞的屬性，是它與某個主張之間的關係。同一則升級消息可以支持「技術面改善」、同時反對「短期拋壓解除」。把立場綁在證據上，就再也拆不開了。

可信度不是主觀判斷也不是 LLM 評分：交易所 API 與官方公告 = high、具名原始報導頁 = medium、聚合轉載與情緒指標 = low。轉載沒取到原頁一律 low，即使它指名了上游發布者。完整表在附錄 A3。

去重刻意只做精確比對：不做語意近似分群——兩天內驗不完的東西不放進 MVP。

噪音處理哲學：不主觀刪源，而是分級加隔離——低訊號社群鎖在 low，結構上無法驅動高信心結論。這比直接刪除更可回溯。

回應第 2 頁的風險 02（50 秒）：判定條件是三個 AND，全部 deterministic：同一個 Claim 同時有 supports 與 opposes、雙方 reliability 都至少 medium、且來自不同 independence group。

順序很關鍵：衝突是在 Arbiter 拿到證據之前就判定並鎖好的。模型收到的 payload 裡，那個結論的 confidence 上限已經被壓成 low 了。它不是「被說服要保留反方」，是沒有相反的選項可選。

反過來的誠實：找不到可信反方訊號時，系統會列出已查詢的來源，並把「未找到反方」明確列為限制——不假造一個反方來湊平衡。

報告第 5 段「主要反方或矛盾證據」是固定段落，不是有才寫。

回應第 2 頁的風險 03（60 秒）：完整失敗矩陣在附錄 A1，這裡挑五個代表。

特別強調一條：baseline 市場源失敗時，我們產生誠實的 partial／degraded，不宣稱切換到第二個 live provider——因為 MVP 根本沒有第二個。宣稱有備援但其實沒有，比沒有備援更糟。

降級不是靜默的：每一種降級都在三個地方留下痕跡——UI 的來源狀態、execution_log.jsonl 的 typed degradation event、報告的「限制與資料缺口」段落。評審看得到系統知道自己缺了什麼。

三種 run mode 不可混淆：official 禁 fixture 與預存答案；rehearsal 可用 fixtures 但必須標示；demo 必須顯示 recorded fallback 橫幅與原始取得時間。三者在 UI、log 與 run_config.json 都清楚可辨。

時間工程（45 秒）：完整八個里程碑在附錄 A2。這裡只要記三個數字。

720：第 12 分鐘停止分析，取消所有還在跑的外部與 LLM 呼叫。780：第 13 分鐘前四個檔案落盤。900：剩下兩分鐘全部留給現場抖動與評審操作。

為什麼 retry 不能加預算：如果 retry 可以延長時限，那 deadline 就不是 deadline 了。單次外部呼叫上限 45 秒、最多 retry 一次、schema repair 最多一次——全部共用原 stage 預算。

deadline 較短時：各 stage 按比例縮放，並保留最後 20%（可能時至少 60 秒）給 deterministic finalize。這條保證了任何時間預算下都交得出 artifacts。

加分層（50 秒）：這一層只是把既有的嚴謹度「顯影」出來，不會變成第二個真相來源。全部 deterministic、幣種無關、可誠實降級。

Trust Scorecard 的自我約束：必須與 confidence 一致——少於 2 個獨立群不得標 strong；有 material conflict 時一致性不得高於 weak。而且不輸出未校準的百分比，只給等級加原始計數（例如「3 個獨立群」）。只為 conclusion 產生，fact 與 inference 不產。

Market Regime 的幣種無關性：門檻一律拿該資產自己的 rolling 歷史比（百分位／z-score），不用跨幣絕對值。缺 bar 就標 unavailable。

雙幣比較的關鍵理由：比較只有在兩個資產的證據進入同一個 Arbiter payload 時才存在。而且跨幣永遠不比 base-asset volume（單位不同），只用報酬差、各自百分位、相對強弱比值。

收尾（30 秒）：回到第 2 頁的四個問題——資料從哪來（Evidence Ledger）、怎麼推論（fact → inference → conclusion）、哪些證據衝突（material conflict 雙方保留）、哪些限制影響結論（限制段落與 Trust Scorecard）。四個都在 artifacts 裡，評審可以自己查。

三個補充賣點（有時間才講）：幣種無關——pipeline 以 {asset} 為參數，沒有 if asset == "BTC" 這種分支。可離線驗證——外部世界全關在 port/adapter 之後，預設測試套件完全不碰外網。單機可交付——單一 non-root Docker image → ECR → 單台 EC2，Bedrock 走 instance role，不把長效 key 烘進 image。

H3 一定要主動說：Bull／Bear／Judge 多輪辯論只有預設關閉的 stub，我們不宣稱 live 啟用過。主動揭露比被問出來好。

high≥2 個獨立群的 high／medium 支持、無 material conflict、無關鍵缺源，且關鍵數值全由 deterministic 工具產生

insufficient_data=true → 整體 low

只有 low 證據 → 該 claim low
唯一當期證據是 stale cache → 當期狀態主張 low
模型自評的 confidence 只會被政策調低，永遠不會被放寬。禁止把三級信心描述成未校準的精確機率。
